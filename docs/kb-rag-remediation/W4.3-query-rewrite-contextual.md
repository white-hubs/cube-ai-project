# W4.3 — 查询改写与上下文增强边界（F-09 / F-13）

## 1. 已核实事实

- Agent 持有会话历史和当前意图，KB core 不持有完整对话语境。
- KB 当前已有确定性检索文本：正文之外会组合文件名、`headingPath`，表格/VTT 等块还包含表头或时间信息。
- 当前 KB 实现中的 LLM query rewrite 与 contextual prefix 会新增模型调用、超时、费用和不可复现变量；contextual prefix 还会触发全量重嵌。

因此，“成熟知识库必须在 KB 内再做一次 LLM 改写/摘要”是错误前提。能力是否成熟取决于检索效果和可控性，而不是模型调用数量。

## 2. 本轮决策

### 2.1 Query rewrite 归 Agent

- 对话省略、指代消解、意图补全由 Agent 完成。
- Agent 首次 grounding prefetch 可继续使用原始 prompt，以控制首包延迟。
- 首次结果不足时，Agent 可生成独立、可检索的问题，再调用知识检索工具。
- KB core 只负责确定性 normalization、双腿召回、融合、rerank 与过滤；不得改写 tenant、ACL 或服务端过滤条件。
- 删除/停用 KB 内 `RETRIEVAL_QUERY_REWRITE_*` 及其 LLM 调用路径，避免 Agent 与 KB 双重改写。

### 2.2 保留确定性上下文，移除 LLM contextual prefix

- 保留 `headingPath`、文件名、表头、VTT 时间等确定性 `embeddingText` 组合。
- 当前交付不调用 LLM 为每个 chunk 生成上下文摘要。
- 删除/隔离 `INGESTION_CONTEXTUAL_PREFIX_*` 活跃路径；不得因开关误开触发隐性模型费用和全库重嵌。
- 如未来真实数据证明确定性上下文不足，LLM contextual retrieval 作为独立实验重新立项，必须单独评估质量、重嵌成本、延迟和可复现性。

## 3. 实现步骤

- 删除 RetrievalService 内的 KB LLM query rewrite producer，保留确定性 query normalization。
- 删除未使用的 query rewrite/contextual prefix 配置和 DI 接线；如兼容期必须保留 env，只接受并记录 deprecated，不能生效。
- 为 Agent 二次知识查询补充独立问题的行为测试；不得重复改写已经独立的问题。
- 为 `embeddingText` 增加确定性上下文测试：标题层级、表格表头、VTT 时间、普通正文。
- 在评测结果中区分“Agent 改写查询”与“原始 query”，不得把 rerank 收益归因给改写。

## 4. 门阀验收

| ID | 要求 | 验证 |
| --- | --- | --- |
| W4.3-H1 | KB core 不发起 query rewrite LLM 调用 | 单测 + DI review |
| W4.3-H2 | KB ingest 不发起 contextual prefix LLM 调用 | 单测 + DI review |
| W4.3-H3 | 确定性 `embeddingText` 保留文档结构上下文，display text 不被污染 | chunk fixture |
| W4.3-H4 | Agent 二次检索使用独立问题，tenant/ACL 仍由 host/KB 强制注入 | engine + port 测试 |

## 5. 成本与偏差提醒

- Agent 改写不是天然更好：可能丢失专有名词或把不确定意图具体化，必须保留原始问题用于 trace/eval。
- 同一轮同时开启 Agent 改写和 rerank 会造成归因混淆；实验应分别记录 feature/version。
- 若 Agent 已把问题改成独立问句，KB 再改写通常只增加延迟和费用。
