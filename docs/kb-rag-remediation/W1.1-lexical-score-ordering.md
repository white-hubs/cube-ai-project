# W1.1 — 词法检索：SQL 预评分排序后再截断（F-03 正确性）

> 修订说明（对照 plan-review G-01）：原「去掉 ORDER BY + LIMIT 放大」**不满足**「候选集内最高 K 条」验收——无 ORDER BY 的 LIMIT 返回任意子集。SQL 预评分从「可选」升为**必须**。

## 1. 背景与问题

[`searchLexicalChunks`](../../packages/kb/core/src/modules/vector-store/infrastructure/qdrant/document-chunk.repository.ts) 当前：

1. `WHERE … LIKE '%term%'` 命中候选
2. `ORDER BY chunk_index ASC LIMIT topK*4`
3. JS 里 `calculateLexicalScore` 再排序取 `topK`

**缺陷**：词法高分但 `chunk_index` 靠后的 chunk 会在步骤 2 被截掉，召回有损。
报告 F-03 Major。本波只修正确性，不做 FULLTEXT（见 W3.4）。

## 2. 目标 / 非目标

**目标**

- 返回的 topK 必须是「当前 LIKE 候选集内、按与 JS 同权的评分排序后最高的 K 条」
- 预取窗口内的排序由 **SQL `ORDER BY score DESC`** 保证，不得依赖无序 LIMIT
- 行为对 `documentId` / `documentIds` / tenant scope 保持不变
- 单测覆盖「高 chunk_index + 高分」可召回，且在 **候选数 > candidateLimit** 的合成场景下仍优先高分
- 先在 W1.4 保存旧路径 E1 before，避免把改造结果误登记成基线

**非目标**

- 不上 MySQL FULLTEXT / ngram
- 不改字段权重语义（与现有 `calculateLexicalScore` 权重对齐）
- 不解决 LIKE 全表扫描性能（W3.4）

## 4. 设计（修订后·选定）

### 必须：SQL 预评分 + ORDER BY score DESC LIMIT N + JS 精算

1. 在 SELECT 中构造与 JS 权重一致的 **粗糙/等价** score 表达式（各字段对 query/terms 的 LIKE 命中布尔加权求和）
2. `ORDER BY lexical_pre_score DESC, chunk_index ASC LIMIT :candidateLimit`
3. JS 再用现有 `calculateLexicalScore` 精算，`.toSorted` 后 `slice(0, topK)`

说明：目标既然声称返回“完整 LIKE 候选集按 JS 分数最高的 K 条”，SQL 预评分就必须与目标分数排序等价，或提供数学上的保序证明。单个“高分远在窗口外”用例只能证明一个反例被修复，不能证明近似评分对所有候选保序。若做不到，应诚实把目标改成“candidate recall 达到预登记门槛”，并通过 E1/E3 衡量，而不能继续宣称精确 topK。

### 配置（唯一入口，消除 500/2000 矛盾）

```ts
// app.config — 仅此一处
lexicalCandidateLimit: envNumber("LEXICAL_CANDIDATE_LIMIT", 500)
```

- 公式：`candidateLimit = max(topK, config.lexicalCandidateLimit)`
- **禁止**再写死 `min(..., 2000)` 第二套上界；若需封顶，只在 config 默认/文档中体现（默认 500，运维可调高）

### SQL 权重对齐（与 JS 一致）

| 字段 | exact（含整 query） | term |
| --- | ---: | ---: |
| keywords_text | 4 | 1.1 |
| text_content | 3.5 | 0.8 |
| headers_text | 3.2 | 0.9 |
| start_time / end_time | 3.2 | 0.9 |
| property_namespace | 3 | 0.9 |
| heading_path | 2.8 | 0.8 |
| sheet_name | 2.5 | 0.7 |
| embedding_text | 2.2 | 0.6 |

实现时抽 `buildLexicalPreScoreSql(terms)` 与 JS `calculateLexicalScore` 共用权重常量（同文件 `LEXICAL_FIELD_WEIGHTS`）。

### 4.1 设计约束 / 扩展点

- **约束**：SQL 预评分与 JS 精算权重必须同源常量，禁止两处手写漂移（仓库惯例 C-LAYER：改动落 repository，不散落 controller）
- **扩展点**：W3.4 可替换 SQL 体为 FULLTEXT，但 `LEXICAL_FIELD_WEIGHTS` + JS 精算接口保持；预评分函数签名稳定便于单测注入
- **反模式**：用放大 LIMIT + `ORDER BY chunk_index`「碰运气」召回高分（本波明确禁止）

## 5. 实现步骤

- 抽出 `LEXICAL_FIELD_WEIGHTS` 常量，JS/SQL 共用
- 实现 SQL `lexical_pre_score` 表达式 + `ORDER BY lexical_pre_score DESC`
- `LIMIT` 仅使用 `lexicalCandidateLimit`（与 topK 取 max）
- JS 精算后 `slice(0, topK)`
- 单测 A：高 chunk_index + keywords 精确命中 → top1
- 单测 B（关键）：构造 > candidateLimit 行，高分行 chunk_index 最大；断言仍召回（证明不是靠「放大 LIMIT」碰运气）
- 跑 repository + retrieval lexical 相关测试

## 6. 测试与验收

| 用例 | 期望 |

| 高 chunk_index 的 keywords 精确命中 | 出现在 top1 |

## 7. 风险与回滚

- **风险**：SQL 表达式参数膨胀（terms × fields）→ 限制 term 数（现有上限保持）
- **风险**：candidateLimit=500 大库仍慢 → 正确性优先，性能交 W3.4
- **回滚**：关闭新路径并切回已知正确但可能较慢的保守查询；不得把已知会截掉高分候选的 `ORDER BY chunk_index` 描述为安全回滚
