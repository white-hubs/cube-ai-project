# W2.2 — RetrievalService 接入模型精排并校准阈值（F-01 / F-11）

> 修订说明（对照 plan-review G-02 / G-12）：补齐三条检索路径的精排语义；env 重命名需兼容期。

## 1. 背景与问题

[`calculateRankScore`](../../packages/kb/core/src/modules/vector-store/services/retrieval.service.ts) 在 `retrievalRerankEnabled=true` 时只做规则加分，名称冒充 rerank。
行业基线是 prefetch → **cross-encoder/LLM rerank** → topK。
依赖 **W2.1**（RerankPort）与 **W1.4**（golden 对比）。

## 2. 目标 / 非目标

**目标**

- 检索流水线增加模型精排阶段
- `score` / `rankScore` 优先反映 rerank 分（clamp 到 [0,1]）
- `vectorScore` 仍为 Qdrant dense+sparse RRF 召回分（字段名为历史契约，不是纯余弦相似度）；规则加分仅作 pre-rank / fallback
- 用 W1.4 golden 校准默认 `similarityThreshold`
- rerank 失败时降级到现有规则排序（不空结果）
- **三条 API 路径的精排语义明确且一致（见 §3.1）**

**非目标**

- 多模型 A/B 平台
- 去掉 hybrid RRF
- 一次做完 HyDE（W4.3）

## 3. 目标流水线

```text
embed query
  → dense+sparse RRF + lexical merge   (prefetchTopK: 50~100)
  → quality / keyword filters
  → rule pre-rank (可选，截断到 rerankInputN)
  → RerankPort.rerank(query, texts)     // 见 §3.1 调用次数
  → map scores → threshold + topK
```

### 3.1 多路径精排语义（选定）

| API | 召回 | 模型精排（选定） | topK 语义 |
| --- | --- | --- | --- |
| `search`（全局/单文档） | 一次 merge | **合并候选后 rerank 一次** | 全局 topK |
| `searchByDirectory` | 每文档召回 → merge | **合并后 rerank 一次** | 目录内全局 topK |
| `searchMultiByDocuments` | 每文档独立召回 | **先拼接各文档候选，再统一 rerank 一次**，再按请求 documents 顺序分组截断各 `spec.topK` | 每文档 topK；跨文档相关度可比较 |

**不采纳**「每文档各调用一次 rerank 再拼接」作为默认：成本随文档数线性上升，且无法跨文档比较。

实现要点：

- 将 `modelRerank` 从「藏在 finalize 里隐式每文档调用」改为显式阶段：
  `recall* → mergeCandidates → modelRerankOnce → applyThresholdAndPerDocTopK`
- `searchMultiByDocuments` 重构：先收集全部 `RankedSearchResult`，统一 rerank，再按 `documentId` 分组 `slice(spec.topK)`，最后按请求顺序 flat
- 成本上限：统一候选送入 rerank 前由 `allocateRerankBudget`（或等价）分配 `RERANK_INPUT_TOP_N`。multi-doc 不得按请求拼接顺序直接 `slice(0, N)`；必须定义每文档最低代表性、剩余预算按 pre-rank 分配、去重和稳定 tie-break。
- provider 还必须满足 documents/token 总预算；`INPUT_TOP_N=50` 是项目默认候选数，不是供应商安全证明。当前 vendor 限制见 W2.1 官方来源，运行时以 catalog/provider 契约为准。

### 3.2 设计约束 / 扩展点

- **约束**：流水线显式阶段 `recall* → mergeCandidates → modelRerankOnce → applyThresholdAndPerDocTopK`；禁止藏在 finalize 隐式循环调用
- **扩展点**：`modelRerankOnce` 独立可测；W4.3 多路召回只替换/扩展 merge 前 producer；W4.5 per-KB 只 overlay 阈值与 INPUT_TOP_N
- **反模式**：每文档各调一次 rerank 再拼接（成本线性、不可跨文档比较）
- **反模式**：先按 document 请求顺序 flatten 再截断，导致后置文档候选永远进不了 rerank

## 4. 配置与兼容期

| env | 默认 | 含义 |
| --- | --- | --- |
| `RETRIEVAL_MODEL_RERANK_ENABLED` | `false` → 稳定后 `true` | 模型精排总开关 |
| `RETRIEVAL_RERANK_INPUT_TOP_N` | `50` | 送入 rerank 的候选上限 |
| `RETRIEVAL_RERANK_MODEL` | 空=租户默认 | modelCode |
| `KB_EMBEDDING_TENANT` | `1` | KB 模型 catalog 租户；embedding 与 rerank 共用，禁止被请求 tenant 覆盖 |
| `RETRIEVAL_RULE_BOOST_ENABLED` | 读旧名兼容 | 规则加分（原误称 rerank） |
| `RETRIEVAL_DEFAULT_SIMILARITY_THRESHOLD` | golden 重标定 | 绝对分阈值 |

**兼容期（G-12）**：

1. 新代码优先读 `RETRIEVAL_RULE_BOOST_ENABLED`
2. 若未设置，回退读 `RETRIEVAL_RERANK_ENABLED`（旧名，语义=规则加分）
3. 日志 warn 一次 deprecation
4. 兼容期 ≥ 1 个发布周期后再从文档移除旧名（代码可读一版）

**禁止**在无兼容期时直接删除 `RETRIEVAL_RERANK_ENABLED`。

## 5. 实现步骤

- kb-core 注入 `RerankPort`（可选）
- 抽出 `modelRerankOnce(candidates, query)`
- 重构三条路径满足 §3.1
- `table-row-window` 用 `embeddingText` 送 rerank
- env 兼容读取
- 单测：multi-doc 仅 **1 次** rerank 调用；顺序跟模型分
- 单测：候选总数 > INPUT_TOP_N 且后置文档仍获得预算；改变 documents 请求顺序不改变同一候选集合的资格（稳定 tie 除外）
- 实现并记录 `allocateRerankBudget` 的配额、去重、tie-break 和 token budget 语义
- 增加两层结构化审计日志：KB 路由层记录 `skipped/started/succeeded/fallback`，HTTP provider 层记录实际 `endpointHost/modelCode/status/durationMs`；禁止记录 query、候选文本和 API Key
- rerank 的模型 catalog tenant 与 embedding 一致，固定读取 `KB_EMBEDDING_TENANT`（默认 `1`）；请求 tenant 只负责 KB 数据隔离，不能切换模型凭据
- W1.4 golden on/off 对比
- 校准默认阈值（本 PR 默认 off，不改阈值）

## 7. 风险

- multi-doc 重构触及 API 行为 → 单测锁死「每文档 topK」拼接顺序
- 延迟：+1 HTTP；用 INPUT_TOP_N 控制
- 公平性：全局 cap 会与每文档 topK 冲突；必须显式预算，而非依赖 flatten 顺序
- 阈值尺度 → 必须 golden 标定
- 日志只能证明请求路径、端点和响应状态，不能证明重排质量提升；质量结论仍必须来自 W1.4/E3 对照实验
- 固定模型 catalog tenant 会集中凭据、配额与费用归属；这是与现有 embedding 对齐的事实，不等于完成了按业务租户的成本分摊
