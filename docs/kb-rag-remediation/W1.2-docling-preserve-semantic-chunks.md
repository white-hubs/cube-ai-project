# W1.2 — 保留 docling 语义块，避免默认二次字符切分（F-12）

## 1. 背景与问题

docling 已按语义做 hybrid chunking，但 [`buildDocumentChunks`](../../packages/kb/core/src/modules/ingestion/services/ingestion.service.ts) 在存在 `chunkingOptions` 时总会走 `rechunkParsedChunks`，用字符重叠再切 paragraph/list，破坏语义边界并浪费 embedding 预算。
报告 F-12 Minor（影响实际体验偏 Major）。

关键分支（现状）：

```ts
parsed.chunks && parsed.chunks.length > 0
  ? params.chunkingOptions
    ? this.rechunkParsedChunks(...)  // 只要有 options 就再切
    : this.mapParsedChunks(...)
  : overlapTextChunker.chunkDocument(...)
```

上传路径几乎总是带 `resolvedChunkingOptions` → 几乎总是二次切。

## 2. 目标 / 非目标

**目标**

- docling（或任意 structured parser）产出**经过有效性检查**的 chunks 时优先 `mapParsedChunks`，不盲目二次切
- 仅当调用方显式要求文本再切时才 `rechunkParsedChunks`
  判定条件：`chunkingOptions.textChunkMode === "block" | "merge"`（或新增 `forceRechunk: true`）
- `table-row-window` / `vtt-cue-window` / `properties-group` 继续 `shouldSkipRuntimeRechunk`
- preview 与 ingest 行为一致
- 记录 parser chunk 的字符/token 分布和 embedding 截断情况；超出模型/业务预算时进入显式 fallback

**非目标**

- 不改 docling 远程请求参数
- 不做 Anthropic contextual retrieval（W4.3）
- 不强制迁移历史已二次切的数据（需 reindex）

## 4. 设计

### 决策表

| 条件 | 行为 |
| --- | --- |
| 无 structured chunks | 走 `overlapTextChunker.chunkDocument`（不变） |
| 有 structured + 显式 `textChunkMode=auto` | 有效性检查通过则 `mapParsedChunks`，否则受控 rechunk |
| 有 structured + `textChunkMode` 缺省 | 兼容期按 rollout 登记的旧有效行为；不得静默切默认 |
| 有 structured + `textChunkMode` 为 `block`/`merge` | `rechunkParsedChunks` |
| 特殊 chunkType | rechunk 路径内仍 skip（不变） |

multipart 原文件 preview 与 ingest 必须复用同一 parser route：先走 primary（PDF/DOCX/PPTX 等为 Docling），仅在 primary 失败或 structured chunks 无效时走同一个 fallback。该 preview 只省略 embedding、MySQL/Qdrant 写入和任务调度，不能无条件改走本地 fallback。by-id preview 有 active chunks 时直接返回；普通无 chunks 文档同样从对象存储读取原文件并同步执行该只读 parser route，明确失败/不支持格式才返回空终态。

同步 multipart 与 by-id 原文件 preview 都依赖宿主 HTTP 连接超时覆盖 Docling 的无输出等待时间。`ai-center` 必须在构造 `Application` 时把 `CUBE_SERVER_IDLE_TIMEOUT_MS` 解析值传入 `idleTimeout`；仅声明字段但不传给 Server 属于死配置。当前框架参数单位为毫秒，内部向 Bun 转换为秒，Bun 上限 255 秒；启动日志必须输出最终值。

“可用 structured chunks”至少要求非空、类型受支持、定位信息合法，且长度不超过经目标 embedding 模型和 rerank 路径验证的预算。具体 token 上限不能凭字符数猜测，必须在 E2/目标模型契约中登记；不满足时应标记原因并走受控 rechunk，而不是静默截断。

### API / 文档

- OpenAPI / upload 说明：`textChunkMode=auto` 表示“优先信任通过有效性检查的解析器语义块”，不是无条件保留
- 若产品曾依赖「总是按 chunkSize 再切」，在 changelog 写明 breaking 行为，需显式 `block`
- 省略 `textChunkMode` 的既有调用在兼容期保持旧有效行为；默认切到 `auto` 属能力启用，必须有存量分布、reindex 成本和回滚证据

### 4.1 设计约束 / 扩展点

- **约束**：二次切分行为只由 `textChunkMode`（auto/block）控制，禁止在 parser/ingestion 多处复制 if
- **扩展点**：未来 per-KB 覆盖（W4.5）只 overlay 该开关与 chunkSize，不新开平行配置键
- **反模式**：为「统一长度」在 auto 模式下静默再切 structured 块

## 7. 风险与回滚

- **风险**：依赖「固定 chunkSize」的下游突然变长块，或模型截断导致块尾信息永久不参与向量化
- **成本**：首次 by-id preview 会下载对象并等待 parser；若异步 ingest 同时运行，会有重复 Docling 调用和额外算力成本
- **资源风险**：`CUBE_SERVER_IDLE_TIMEOUT_MS` 是全局 TCP idle timeout，提高到 240 秒会让同步 preview 的静默连接占用资源更久；它保证连接预算，不会缩短 Docling 处理时间
- **缓解**：文档说明；保留 `textChunkMode=block` 旧行为
- **存量**：对 PDF 知识库执行 reindex 后生效
