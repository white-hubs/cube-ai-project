# W1.3 — KnowledgeHit 来源锚点与 chunk 详情（F-04）

## 1. 已核实事实与错误前提

- `SearchItem` 已包含 `chunkId`、`pageNo`、`sectionId` 等定位数据。
- `KnowledgeHit` 当前缺少上述结构化字段，只预留 `link?: string`。
- 仓库没有 `kb://` 的真实 UI/SDK consumer。生成一个无法消费的 URI 不等于“引用能力已完成”。
- `chunk_id` 在 MySQL 中唯一，但只按 chunkId 查询仍可能造成跨租户枚举；详情查询必须附带 tenant scope。

## 2. 本轮决策

- 不生成 `kb://` 或其他伪链接；`link` 保持 optional，只有未来存在真实、鉴权后的 URL resolver 才填写。
- `KnowledgeHit` 增加结构化 `chunkId`、`pageNo`、`sectionId`。为兼容尚未升级的远端 knowledge provider，跨平台 wire schema 将新增字段保持 optional。
- 本仓库 KB 搜索结果必须返回 `chunkId`；不能据此假设所有远端 provider 已同步支持。
- 新增只读 chunk 详情接口：调用方有详情需求时凭 chunkId 查询。
- 详情返回 display text 与来源 metadata；禁止暴露内部 `embeddingText`。

## 3. API 与授权

实际挂载路由（`DocumentController` mount + `@GET("/chunks/:chunkId")`）：

```text
GET /kb/console/documents/chunks/{chunkId}
```

响应至少包含 `chunkId`、`documentId`、`text`、`fileName`、`pageNo`、`sectionId`、`headingPath` 和来源 `metadata`。

授权规则：repository 查询必须同时使用当前 `tenantId`；不存在与错租户统一返回 404，防止枚举。未来如启用非空 ACL，详情接口必须复用同一可见性规则，不能只依赖搜索时已过滤。

## 4. 实现与验收

- contracts additive 扩展 `KnowledgeHitSchema`。
- port 将 `SearchItem` 的结构化定位字段映射到 `KnowledgeHit`。
- chunk repository 增加 tenant-scoped find-by-chunkId。
- controller/service 增加只读详情接口，不复用可更新的内部 entity DTO。
- 测试同租户命中、错租户 404、不返回 `embeddingText`、无 page/section 时字段兼容。

| ID | 要求 | 验证 |
| --- | --- | --- |
| W1.3-H1 | 所有 search hit 均带 `chunkId` | port/controller tests |
| W1.3-H2 | `KnowledgeHit` 结构化携带可用的 page/section | contract + port tests |
| W1.3-H3 | chunk detail 强制 tenant scope，错租户不泄露存在性 | security test |
| W1.3-H4 | detail 不暴露 `embeddingText` | response test |
| W1.3-H5 | 没有真实 consumer 时不生成假 link | contract/port review |

## 5. 后续扩展

真实 UI 路由稳定后，可由 host 提供受鉴权的 link resolver，并在 `KnowledgeHit.link` 中返回真实 HTTP URL。此项不阻塞当前结构化引用。
