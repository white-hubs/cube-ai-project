# W3.1 — Qdrant / MySQL 双写一致性与孤儿清理（F-06）

> 修订说明（2026-08-10 实现复核）：整文档、单块编辑和 ACL/metadata 更新统一采用不可变 point ID 的 versioned generation；删除仍以 MySQL logical delete 为权威。本文同时区分“本地代码证据”和“上线门阀”，不把未跑的 E2 写成已完成。

## 1. 背景与问题

改造前的三类失败窗口如下；这是问题模型，不是对当前工作区代码的描述：

| 路径 | 现状顺序 | 失败窗口 |
| --- | --- | --- |
| `indexDocumentChunks` | Qdrant upsert → MySQL replace | 孤儿向量或 manifest 旧 |
| 单块原地更新 | Qdrant upsert → MySQL update | 同 point ID 的内容或 payload 分叉 |
| `deleteDocument` | Qdrant delete → MySQL logicalDelete（或相反） | 向量已删 manifest 在，或孤儿向量 |

报告 F-06；backlog M6.T6。

## 2. 目标 / 非目标

**目标**

- 上述 **三条路径** 均使用同一 generation/CAS 协议，正常写路径不再原地改写同一个 point
- MySQL active generation 是唯一可见 manifest；Qdrant 候选必须再经 MySQL active generation 校验
- reconcile job 覆盖：活跃 ID 差集、缺失 point 重建和删除后孤儿；内容/payload 版本审计作为独立上线门阀，不得仅凭 ID 对账宣称严格一致
- 失败可重试（outbox/补偿）

**非目标**

- 跨文档分布式事务
- 实时 CDC（增量见 W3.5）
- 一次做完全站历史迁移

## 3. 设计（选定）

### 3.1 整文档索引：版本化 generation

1. 当前 active generation（如 v1）继续服务。
2. 在 MySQL 与 Qdrant 构建 staging generation v2，所有 chunk/point 显式携带 generation/version。
3. 本地实现先校验 v2 的 MySQL/Qdrant 数量和 generation ID 集；上线前还必须完成 payload/version E2。`embedding_fingerprint` 是输入与模型配置的版本标识，不是向量字节校验和，不能单独证明向量值未损坏。
4. 在 MySQL 权威元数据中原子切换 active generation v1 → v2。
5. 异步清理 v1；任一步失败都保留 v1 为 active，不让检索混读“新词法 + 旧向量”。

搜索的 MySQL 与 Qdrant 两腿必须使用同一个 active generation snapshot。删除是例外：MySQL logical delete 立即从权威查询中排除，不等待 generation 切换。

### 3.2 单块编辑

1. 读取当前 active manifest，只替换目标 chunk 的文本/语义字段。
2. 为完整 manifest 建立新 generation；目标 chunk 重新 embed，未变化 chunk 从旧 point 读取并复用向量。
3. 写入并校验新 generation 后，以 tenant-scoped expected-generation CAS 原子切换 active generation。
4. 异步清理旧 generation；失败进入持久 reconcile。这样避免“Qdrant 旧 point 仍存在但 ID 对账看不出来”的同 ID 陈旧写问题。

### 3.3 删除文档

**选定：MySQL 先 logicalDelete（权威）→ Qdrant deleteByDocument → 失败进 reconcile**
避免「向量已删、文档仍可检索预览」的更差体验；reconcile 扫已删文档的残留 point。

### 3.4 reconcile 范围与证据边界

- 已实现：按 tenant/documentId 分页 scroll 全部 Qdrant point，与 MySQL active generation 做 ID 差集；补缺失 point、删孤儿 point、清理已 logicalDelete 文档；补偿消息经 MySQL outbox + BullMQ 持久交付。
- 由不可变 generation 规避：正常整文档、单块、metadata/ACL 更新不会原地复用 point ID，所以旧 payload 与新 active point 不会同 ID 混淆。
- 尚需 E2：人为构造同 ID 旧 payload/version、向量值损坏、进程中断和全库扫描重启。当前 per-document scroll 会遍历完所有页，但没有“全租户扫描任务的持久 cursor”；两者不能混写成已完成。
- 不能成立的推论：`embedding_fingerprint` 相同 ⇒ 向量字节相同。若要求检测任意位翻转，需要保存/比较 vector checksum 或抽样重新 embed，比版本对账有额外存储和模型调用成本。

严格一致性定义与失败矩阵见 [CONSISTENCY-AND-SECURITY-INVARIANTS.md](./CONSISTENCY-AND-SECURITY-INVARIANTS.md)。ID 集合相同只是必要条件，不是任意数据损坏下的充分条件。

### 3.5 设计约束 / 扩展点

- **约束**：MySQL 为权威；编排（index/delete）与 store 适配分离，reconcile 复用同一 diff 逻辑
- **扩展点**：outbox 事件类型可增（`kb.vector.reconcile`），不另造 job 框架
- **反模式**：Qdrant 先删后写 MySQL 导致「向量无、元数据仍在」且无 reconcile

## 4. 实现步骤

- 增加 document active generation 与 chunk/vector generation schema，采用 additive migration
- 构建 staging generation、完整校验、原子 activate、旧 generation 异步回收
- 删除单块原地 upsert 路径；单块编辑改为完整 manifest 的新 generation，只重嵌变化 chunk
- 调整 `deleteDocument` 顺序 + 失败补偿（MySQL logicalDelete → Qdrant → reconcile）
- 共享 `diffDocumentVectors` + `VectorReconcileService`；生产补偿使用持久 `kb.vector.reconcile` job/outbox，in-memory scheduler 只可用于测试或显式非生产环境
- 单测：
  - 整文档第二步失败可收敛（W3.1-H1）
  - 单块编辑 staging 任一腿失败时 active generation 不变（W3.1-H2）
  - 删除后无孤儿向量（W3.1-H3）
  - reconcile 清理故意孤儿 point（W3.1-H4）
  - 同 ID 旧 payload/version 可检测并修复（W3.1-H6，E2 未完成）
  - per-document scroll 超过单页不漏项；若增加全库扫描，再实现其持久 cursor（W3.1-H7）
- 更新 backlog M6.T6（对账能力落地；全量历史迁移仍待运维窗口）
