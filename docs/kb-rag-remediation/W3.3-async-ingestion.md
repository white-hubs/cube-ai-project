# W3.3 — 异步摄入队列（F-16）

## 1. 背景与问题

文档 upload 路径同步执行 parse + embed + index，大文件阻塞请求线程；docling 无独立重试队列。
报告 F-16 Minor（生产体验偏 Major）。依赖 W3.1 状态机更稳。

## 2. 目标 / 非目标

**当前产品运行模式（2026-08-11）**

`INGESTION_ASYNC_ENABLED` 默认值已收回为 `false`：upload、reindex、multipart preview、by-id preview 当前均同步等待处理结果。异步 outbox/BullMQ 实现保留但只作为显式 opt-in 能力；在失败任务管理、readiness/SLO、真实故障注入等门阀补齐前，不得默认开启。若部署环境显式遗留 `INGESTION_ASYNC_ENABLED=true`，仍会启用异步，发布前必须检查并移除该覆盖。

**异步能力目标（当前默认不启用）**

- `upload` / `reindex` API **快速返回** jobId / 文档 `parsing|indexing` 状态
- worker 异步执行 `IngestionService.ingestDocument`
- 失败可重试（次数上限）；状态可查询
- 与现有 `import_job` 表对齐（若已有则复用）
- 满足持久化、原子 claim、lease、at-least-once 幂等、分页恢复和终态失败可见性

**非目标**

- 多租户公平调度算法
- K8s 独立 ingest deployment（可后置）
- checksum / 增量 re-embed（见 [W3.5](./W3.5-incremental-reembed.md)；本波队列应预留 `forceFull` 任务字段以便衔接）
- 独立失败任务管理端、DLQ 查询/人工重放、不可重试错误分类与告警闭环：当前无对应管理端，按 2026-08-11 产品优先级后置至 [W4.6](./W4.6-ingestion-failure-operations-deferred.md)；自动限次重试、持久 `failed` 状态和错误信息不得删除

## 3. 设计（选定）

QUEUE-01 已选定：复用仓库现有 **MySQL outbox + relay + BullMQ**，消息契约沿用 `kb.ingest.v1`。outbox claim 使用既有 `FOR UPDATE SKIP LOCKED` 语义；不再把进程内数组/定时器描述为生产持久队列。

异步能力显式开启时：

1. HTTP：落对象存储 + 建 document + enqueue `kb.ingest`
2. outbox relay 发布 BullMQ；Worker 消费 → ingest → 更新 parse/index 状态
3. 客户端轮询 document 状态或 job 状态

outbox 领取与 BullMQ 交付按 at-least-once 设计。ingest 以 `importJobId` 同时作为 outbox/BullMQ 幂等键，并以 document 的 `active_generation_job_id` 单调水位阻止旧任务晚完成覆盖新 generation；不能只写一个实现中不存在的抽象 `(operation, expectedVersion)`。启动恢复不能依赖“只恢复前 200 条”。详细不变量见 [CONSISTENCY-AND-SECURITY-INVARIANTS.md](./CONSISTENCY-AND-SECURITY-INVARIANTS.md) §7。

启动兜底恢复使用 `(create_time, id)` keyset 分页扫描全部 `pending/processing` import job，并在 tenant context 内重排队；`limit` 是页大小而不是总上限。worker 先创建，恢复扫描随后在后台运行；HTTP bootstrap **不得等待整个恢复扫描完成**。恢复开始、完成（含 recovered 数量）和失败必须有日志，失败由持久 MySQL job 留待下次恢复，不能形成未处理 Promise。

当前共享 `outbox_events.tenant` 为数值列，因此代码拒绝非数字 tenant ID。现有平台租户为数字时可用；若未来允许 UUID/任意字符串 tenant，这是一项 schema 迁移前置，不能在 scheduler 中静默强转。

W3.3 的异步边界只覆盖 upload/reindex 的持久摄入，不改变 preview 的“本次请求返回可展示分段”语义。by-id preview 优先读取 active generation 的持久化 chunks；普通未拆分文档从对象存储读取原文件并在当前请求内执行只读 parser/chunker，不 embed、不写 MySQL chunks/Qdrant、不创建 job。明确失败/不支持格式返回对应终态。该路径可能与正在运行的异步 ingest 重复解析，当前接受这项延迟/算力成本；后续应以 checksum+chunking config 缓存或 singleflight 降低重复工作，而不能用快速 `200 + items=[]` 冒充预览成功。

并发：每租户/全局 worker 并发上限 env 可配；当前每租户 semaphore 是**进程内**的，多副本总并发会按副本数放大。生产容量必须按 `副本数 × 单副本上限` 计算，或后续改为 Redis/队列级全局限流。必须观测 queue depth、oldest age、retry、dead-letter 和 tenant 占用。`upload p99` 目标值在测量旧路径基线和前端超时预算后由 owner 登记，不能只写“快速”。

### 3.1 Redis 配置契约

KB ingest worker、vector reconcile worker 与负责投递它们的共享 outbox relay 必须采用同一优先级：

1. `AGENTIC_ENGINE_REDIS_URL`（显式 worker/engine override）
2. `REDIS_URL`（仓库和 ai-center 现有标准配置）
3. `BUN_REDIS_URL`（兼容入口）
4. `redis://127.0.0.1:6379/0`（仅本地 fallback）

空字符串视为未配置；解析必须保留 username/password、`rediss:` TLS、port 与 DB index，日志不得输出凭据。2026-08-10 两次定位确认：ai-center 已通过 `REDIS_URL` 连接 SFID，但 KB BullMQ 和共享 outbox relay 分别只读取 `AGENTIC_ENGINE_REDIS_URL`，会错误退回 localhost。worker 优先级由 `bullmq-connection.test.ts` 固化，relay 优先级由 `bullmq-enqueue.adapter.test.ts` 固化。

### 3.2 启动与 readiness 边界

- 创建 BullMQ worker 是启动步骤；全量恢复扫描是后台可靠性步骤，不得阻塞 HTTP listen。
- outbox relay 的 Redis leader election 不得在 HTTP listen 前被同步等待。ai-center 先输出 `ai-center.listening`，再后台启动 relay；默认开启以匹配持久摄入，紧急回滚可设 `AGENTIC_ENGINE_ENABLE_OUTBOX_RELAY=0`。
- descriptor 完成后的无日志区间必须逐 domain 标识 migration starting/completed，并标识 HTTP listen starting；若仍停滞，可区分 KB V006 DDL/锁等待和 relay/worker 问题，不能继续凭最后一条日志归因。
- 服务进入监听不等于恢复已完成。queue/Redis/MySQL 可用性应进入 readiness/运维观测；当前以显式 startup recovery 日志兜底，readiness 探针仍是上线前补项。
- `DescriptorLoader` 的可降级 ENOENT 警告在打印 `startup descriptor loading complete` 后已经结束，不得把后续 worker/DB 阻塞误判成 descriptor 扫描问题。

### 3.3 MySQL 事务与 DI 边界

异步 upload/reindex 的 document、`import_job` 与 `outbox_events` 必须使用 **KB 自己的 mysql2 同一连接**提交。宿主注入的 `DATABASE_SERVICE_TOKEN` 实例同时提供 `runInTransaction`；事务期间，repository 与 outbox scheduler 发出的所有 `DatabaseService.query` 由异步上下文路由到同一个 `PoolConnection`，成功 commit，任一 SQL/入队写失败则 rollback。嵌套调用采用 REQUIRED 语义，复用外层事务。

不得给 `DocumentService` 直接注入框架 `TransactionManager`，也不得在 KB repository 上使用与当前 mysql2 adapter 不同会话体系的 `@Transactional()`：两者既不能证明 KB SQL 加入同一事务，前者还曾在 2026-08-10 导致所有 `DocumentService` 路由在容器解析阶段报 `Provider not found for token: TransactionManager`，preview 返回 503。DI 回归测试必须从真实 `AiCenterKbHttpModule` 解析 `DocumentService`，不能只在单测中手工 `new DocumentService(...)`。

对象存储不属于 MySQL 事务：upload 先写对象，数据库事务失败后 best-effort 删除对象；删除也失败时仍可能留下 storage orphan，需要运维 reconcile/清理任务。该补偿窗口不能被表述为“跨 MySQL 与对象存储的完全原子事务”。

### 3.4 设计约束 / 扩展点

- **约束**：复用仓库既有 outbox / `import_job` 惯例，**禁止**为本波另造第二套 job 框架
- **扩展点**：消息 schema 预留 `forceFull`（衔接 W3.5）；worker 与 HTTP 进程可同仓拆分
- **反模式**：upload 同步 embed 后再改异步却保留双路径无 feature flag

## 4. 实现步骤

- 复用现有 outbox schema、relay、BullMQ factory 与 `kb.ingest.v1` contracts
- 默认同步执行 upload/reindex；`INGESTION_ASYNC_ENABLED=true` 显式开启时，才通过 KB mysql2 transaction runner 在同一连接写 document/import job + outbox 并快速返回；禁止注入框架 `TransactionManager` 冒充该事务
- worker bootstrap 接入 BullMQ；删除生产进程内 scheduler 依赖
- KB BullMQ 连接兼容现有 `REDIS_URL`；两个 worker 共享同一解析器与配置优先级测试
- 共享 outbox relay 同样兼容 `REDIS_URL`，并移到 HTTP listen 后后台启动；输出 starting/started/failed 或 disabled 状态
- worker 先启动、MySQL 恢复扫描后台执行；为 begin/complete/fail 增加可定位日志
- 保留自动限次重试和持久失败状态；独立 DLQ 管理/重放进入后续管理端规划
- 集成测试：小文件异步最终 indexed
- preview 测试：已有 chunks 直接返回；普通无 chunks 文档同步执行只读拆分并返回 items；明确失败/不支持格式返回终态

## 5. 验收

必须按运行模式分别验收，禁止混用结论：

**当前默认同步模式**

- upload/reindex 返回成功时，parse、embed、MySQL/Qdrant 索引已完成；失败在本次请求明确返回。
- preview 在本次请求返回可展示分段，不能用快速空数组冒充成功。
- p95/p99 包含完整处理时间；客户端、网关、Bun idle timeout 和上游 timeout 必须共同覆盖该预算。

**显式 opt-in 异步模式**

- upload/reindex 快速返回持久 job/处理中状态，p99 不再包含整篇 embed 时间。
- 失败任务可在限次内自动重试，超限进入持久失败终态，状态机对前端可见。
- 默认启用前还必须补齐 readiness、队列 SLO、真实故障注入和 W4.6 的产品准入条件。
